# CCC Meeting Capture

Instrumentation for a QI study measuring **what the committee's spontaneous recall misses**.

During a CCC meeting you start a session, and from then on every resident page you open
gets a slide-over drawer where you record, in this order:

1. whether the room already knew about any open action items from last cycle,
2. what the room produced about this resident *before you said anything*,
3. what you contributed, and what visibly changed as a result,
4. what was agreed, and whether the group's read shifted.

When no session is active, nothing about the app changes — no banner, no drawer, no extra
buttons on the resident page.

---

## Running a meeting

**Start** — "Start CCC" in the header. Set the date (defaults to today) and the cycle label
(prefilled from the last meeting, e.g. `Fall 2026`). Only one meeting can be open at a
time; if you click Start twice you get the same meeting back, not two.

**During** — a thin amber banner sits at the top of every page. Open a resident and a
pill appears bottom-right showing how many contributions you have logged for them;
`Ctrl+Shift+L` toggles the drawer. Simply visiting the resident page starts their log, so
the "minutes on this resident" clock is running whether or not you open the drawer.

Every field autosaves. There is no save button and no confirmation dialog anywhere.
Tapping a selected choice again clears it, which is the undo for a mis-tap. All fields are
optional — a half-filled log is valid data.

**The one field to always tap: Spontaneous input (None / Thin / Substantial).** Opening a
resident's page creates their log, so a page you opened just to look something up produces a
row that otherwise looks identical to a resident you discussed and recorded nothing about.
Tapping Spontaneous input — *including `None`* — is what marks the row as a real discussion,
and `None` is itself a finding worth having. Everything else can stay blank.

**If the backend is unreachable** the drawer keeps working. Writes queue up in the browser
(the pill and banner show how many are waiting) and retry with backoff until they land.
The queue survives a page reload, so nothing typed mid-meeting is lost. Ending a meeting
waits for the queue to drain first.

**End** — "End meeting" in the banner.

---

## Study codes

Residents appear in every export as `R001`, `R002`, … and never as a name or an internal id.

A code is minted the first time a resident is discussed in a CCC (or first given an action
item) and stored on the resident record, so it is stable for the life of the study. The
order codes are handed out is the order residents are first discussed — deliberately *not*
alphabetical, so the sequence cannot be used to reconstruct a name ordering.

The code is also **copied onto the resident's CCC rows** when they are written. That is what
lets the study data survive a resident being removed from AUC: their log rows stay, their
`resident_id` goes NULL, and the exports still work. Codes are never reused, even after the
resident record is gone.

### `ccc_action_items` — what was agreed

| Column | Notes |
|---|---|
| `id` | 8-char text id |
| `resident_id` | → `residents`, `ON DELETE SET NULL` |
| `study_code` | Snapshot |
| `created_session_id` | The meeting where it was agreed |
| `item_text` | Free text. (Named `item_text`, not `text`, to stay clear of SQL keyword trouble in the partial-update builder. The API request field is still `text`.) |
| `owner` | Free text |
| `status` | `open` \| `done` \| `no_longer_relevant` |
| `created_at`, `resolved_at` | `resolved_at` is set when status leaves `open`, cleared if it returns |

### `ccc_action_item_checks` — the recall experiment

Unique on `(action_item_id, session_id)`: one row per item per meeting.

| Column | Notes |
|---|---|
| `id` | 8-char text id |
| `action_item_id` | → `ccc_action_items`, cascades |
| `session_id` | → `ccc_sessions`, cascades |
| `checked_at` | First tap |
| `recalled_by_room` | 0/1 — the room brought it up unprompted |
| `surfaced_by_auc` | 0/1 — you had to surface it |

Both flags can be 1. The two buttons write to the same row and the flags are **ORed** in,
so tapping "Room remembered" and then "I surfaced it" records both rather than the second
overwriting the first.

### Change to an existing table

One column is added to `residents`: `study_code TEXT`, unique where not null. Nothing else
in the existing schema is altered, and no existing data is rewritten.

## Retrieval timing

`retrieval_seconds` answers "how long did it take me to find the thing I just said?"

The clock starts when the drawer opens on a resident. Each logged contribution records the
seconds since the clock last started, then restarts it — so the second contribution is
timed from the first, not from when the drawer opened. There is no manual stopwatch.

If the clock was not running (a contribution logged in some path that never opened the
drawer) the field is left NULL rather than filled with a differently-defined number.

Cumulative time is not lost by this choice: `contribution.created_at − log.opened_at` is
always available in the database, so a "total elapsed" measure can be recomputed at any
time.

**Caveat for analysis:** these are wall-clock seconds during a live meeting, so they
include interruptions, and they measure retrieval-plus-formulation, not retrieval alone.

---

## Idempotency

The browser generates the row ids and sends them, and every insert is `INSERT OR IGNORE`.
So a double-clicked button, and a retry after a response was lost on the network, both
result in exactly one row. `POST /api/ccc/sessions` returns the already-open meeting rather
than opening a second one, and `POST /api/ccc/resident-logs` returns the existing log for
that session and resident.

## Exports

Three CSVs, from the **Study Data** page in the header. Each covers all sessions to date.
Files are UTF-8 with a BOM so Excel opens them correctly, and are named
`ccc-<export>-<today>.csv`.

### `include_text`

Off by default. With it off, the free-text columns are **absent from the file entirely** —
not blank. With it on, they are **appended after** the coded columns, so the coded columns
are always in the same positions.

The columns this governs: `room_raised_notes`, `pushback_note`, `closing_notes`, `detail`,
`item_text`, `owner`.

Consequence worth knowing: the two variants have different column sets, so an analysis
script has to tolerate both (read by column name, not position). Free text is where
identifiable narrative hides, which is why the default is to leave it out.

An export never contains a name, a `resident_id`, a photo filename, a medical school, or an
interests field. This is enforced in code — `ccc_export.py` raises rather than emit a file
containing a forbidden column.

### `ccc-resident-sessions.csv`

One row per resident log, i.e. one row per resident per meeting.

| Column | Meaning |
|---|---|
| `study_code` | `R001`, … |
| `session_date` | Meeting date |
| `cycle_label` | e.g. `Fall 2026` |
| `touched` | **0/1. Filter on this first.** 1 means this resident was actually discussed; 0 means the page was opened but nothing was ever recorded — see "Incidental page visits" below. |
| `pgy_year_at_session` | PGY at the time of this meeting, not today |
| `room_input_level` | `none` \| `thin` \| `substantial`; blank if not recorded |
| `roles_spoke` | Pipe-delimited, fixed order, e.g. `inpatient_attending\|chief` |
| `referenced_written_eval` | 0/1; blank if not recorded |
| `n_todo_surfaced` | Count of your contributions of that type… |
| `n_eval_content` | |
| `n_pattern_trend` | |
| `n_discrepancy` | |
| `n_outcome_no_effect` | Count of your contributions with that outcome… |
| `n_outcome_added_detail` | |
| `n_outcome_changed_assessment` | |
| `n_outcome_new_action_item` | |
| `group_read_shifted` | 0/1; blank if not recorded |
| `pushback` | 0/1; blank if not recorded |
| `minutes_on_resident` | Minutes from `opened_at` to whichever endpoint `duration_basis` names. Blank when there is no endpoint at all. |
| `duration_basis` | **Read this before using the previous column.** `log_closed` (you tapped "Done with this resident" — the clean case), `session_closed` (the meeting ended with this resident's log still open, so the figure runs to the end of the meeting and is an over-estimate), `last_contribution` (neither was closed; runs to your last contribution, an under-estimate), `none` (nothing to measure — the column is blank). |

| `closing_notes` | *(include_text)* |

The eight `n_*` columns are always numeric, `0` rather than blank, and exclude voided cards.

#### Incidental page visits, and the `touched` column

**Every resident log produces a row here, including empty ones.** A log is created as soon as
you open a resident's page during a meeting — you do not have to open the drawer — so a
resident whose page you opened but recorded nothing about appears as a row of blanks and
zeros. A resident never opened during the meeting produces no row at all.

That is what `touched` is for. **Filter `touched = 1` before computing anything**, or
incidental page visits will dilute every denominator you build.

`touched` is 1 when any of these is true:

- `room_input_level` is set — *the one that matters, see the rule below*
- any other coded field is answered: `roles_spoke` (a non-empty list),
  `referenced_written_eval`, `group_read_shifted`, `pushback`
- any surviving (non-voided) contribution exists
- any free-text field is non-empty: `room_raised_notes`, `pushback_note`, `closing_notes`
- the log was explicitly closed with "Done with this resident"

The last two clauses go slightly beyond "coded fields": typing a note or tapping Done is
unambiguous evidence of a real discussion, and treating those rows as untouched would throw
away genuine data. Only the 0/1 result is ever exported, so this stays true with
`include_text` off.

> #### Rule for whoever runs the meeting
>
> **Always tap Spontaneous input for every resident you actually discuss — including
> `None`.**
>
> `None` is a real finding: it means the committee produced nothing unprompted, which is
> precisely what this study is trying to measure. Leaving the field blank is not the same
> claim; blank is what marks a row as an incidental page visit.
>
> Tap it and `touched = 1` even if you record nothing else. Skip it and a discussion where
> the room said nothing and you added nothing is indistinguishable from a page you opened by
> mistake — and those are opposite findings. The drawer labels the field
> *"always tap one, even None"* as a reminder.

### `ccc-action-items.csv`

By default, **one row per check** — that is, one row per (action item × meeting in which it
was checked). An item created and never revisited produces no row.

| Column | Meaning |
|---|---|
| `study_code` | |
| `item_text_present` | 0/1 — whether the item has any text. The text itself is only present with `include_text`. |
| `created_cycle` | Cycle label of the meeting where the item was agreed |
| `check_cycle` | Cycle label of the meeting where it was checked |
| `had_check` | *(only with `include_unchecked`)* 0/1 |
| `recalled_by_room` | 0/1 |
| `surfaced_by_auc` | 0/1 |
| `current_status` | `open` \| `done` \| `no_longer_relevant`, as of now |
| `item_text` | *(include_text)* |
| `owner` | *(include_text)* |

**`?include_unchecked=true`** widens this to one row per action item, with items nobody
revisited included (blank check columns, `had_check=0`). You want this if you are computing
a recall *rate*: the default grain gives you the numerator only. Add the parameter to the
download URL by hand.

### `GET /api/ccc/export/session/{id}`

The whole of one meeting as JSON — sessions, logs, contributions, action items and checks.
Intended for backup and debugging. Keyed by `study_code` only, like the CSVs, so it carries
no names either. Includes voided contributions (with their `voided` flag), unlike the CSVs.

## Notes for whoever analyses this

- **`referenced_written_eval` and `contribution_type='eval_content'` are not independent.**
  The first is "somebody in the room cited a written evaluation"; the second is "I brought
  written evaluation content in". They measure closely related things from different
  actors, and a resident-level model should not treat them as separate signals.
- **`room_input_level` is a single rater's judgement**, made live, by someone who is also
  participating in the meeting. Treat it as ordinal and expect rater drift across cycles.
- **`outcome` is the operator's read of the room's reaction**, not a measured change in any
  document. `changed_assessment` means it looked like the committee changed its mind.
- **Blank ≠ zero** in every 0/1 column: blank means the question was never answered, which
  during a live meeting is common and is not the same as a "no".
- Deleting a resident from AUC leaves their CCC rows in place with a NULL `resident_id`.
  Deleting a *session* would cascade and remove its logs, contributions and checks; there
  is deliberately no endpoint that does this.
